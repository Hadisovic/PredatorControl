# Security and reliability audit

Review dates: 2026-11-02 through 2026-11-03 (Asia/Amman). Baseline: `3468846` on `revisions`. This review covers source and controlled local tests, not a certification of hardware or an absence of vulnerabilities. Existing distributed executables are separate artifacts and are not replaced by this audit; private publish candidates are build verification only.

## Threat model established before remediation

The WinForms process requests administrator privileges (`src/app.manifest`). Classic UI, the embedded React/WebView2 bridge, startup preference restoration, Game Sync and hardware hotkeys converge on the capability checks and serialized write gate in `WmiController`. There is no separate privileged broker. A compromise of this process therefore has administrator impact.

| Boundary | Caller/input | Authority and side effects | Threat and review focus |
|---|---|---|---|
| Process startup | CLI flags, executable path | Administrator; diagnostics, repair, optimization, headless battery task or GUI | Writable startup images; diagnostic output paths; single-instance bypass in explicit maintenance modes |
| Single-instance IPC | Local pipe clients, text commands | Same-user pipe ACL; UI activation, mode cycling, exit | Same-user medium-integrity callers, other sessions/users, squatting, framing, cancellation and flooding |
| Embedded UI | Bundled JS; JSON messages | Elevated host; explicit controls and settings | Untrusted navigation/message origin, malformed payloads, exposed native capabilities; CSP and blocked permissions/downloads |
| Updates | Fixed GitHub release API, asset URLs, checksums, executable | Elevated protected staging; batch replacement and relaunch | Compromised release account/CDN, integrity versus independent authenticity, redirects, bounds, version rollback, replacement races |
| Persistent data | HKCU/HKLM preferences and per-user JSON/log files | Elevated reads/writes; supported hardware preferences | Same-user malicious configuration, filesystem redirection, truncation, oversized data; values must still pass hardware gates |
| Startup tasks | UI request, current image, generated XML | Elevated logon task and SYSTEM battery task | Protected executable/ancestors and locked task XML; no portable-image promotion |
| OEM services | Fixed service names, HKLM registration, DriverStore discovery | SCM changes, signed Acer executables and INF installation | Writable/reparse paths, publisher identity, catalog membership, consent and launch arguments |
| OEM IPC | Loopback TCP/named pipes and binary/JSON replies | Read-only discovery or capability-authorized hardware writes | Endpoint PID/signature trust, malformed lengths/opcodes, deadlines, ambiguous acknowledgements and retries |
| Native code | Windows DLLs, embedded WebView2 loader, System32 NVML, ETW/display APIs | Elevated native calls | Loader search paths, ACLs/held handles, layouts, allocation bounds and disposal |
| Build/distribution | NuGet/npm, scripts, tracked binaries and CI | Build-time execution; eventual release publication | Compromised dependencies, unpinned actions, artifact/source drift, signing keys, excessive workflow permissions |

External websites cannot normally navigate the WebView or use host objects. A compromised bundled dependency executes within the trusted UI and still reaches only the explicit native dispatch; hardware validation remains essential. Different local users should have neither pipe access nor write access to protected staging. Same-user non-elevated applications can edit user settings and paths, and are treated as untrusted across the elevation boundary. A compromised release source must not become an independent signature authority. Corrupted OEM responses must not report a hardware change as confirmed.

## Baseline

Application Release build: PASS, zero ordinary-build warnings/errors. Frontend production build/lint: PASS. Existing tests: 207 compatibility, 24 keyboard, 8 security, 10 frontend and 3 scanner checks passed. NuGet transitive vulnerability audit and npm audit: PASS, zero reported vulnerable packages. An opt-in all-rules .NET analyzer build of the baseline subsequently produced 1,084 warnings and zero errors; ordinary build success does not mean those warnings are absent. Test results describe synthetic fixtures; no hardware writes, service modifications, scheduled-task registration or elevated updater execution were performed.

## Architecture, compatibility and inventory conclusions

- Source targets .NET 10 Windows, requests administrator privileges and documents Windows 10/11 x64. NuGet inputs are WebView2 `1.0.3650.58`, System.Management `10.0.12` and ServiceController `10.0.12`; application runtime patch is `10.0.14`. Frontend uses React/React DOM `19.2.6`, Vite `8.3.5` and the existing pinned TypeScript/lint toolchain. No dependency was added or upgraded in this pass.
- Reviewed compiled profiles include PH16-71, PHN16-71, AN515-54 (Octavia_CFS), AN515-58, AN515-46/47 and AN517-42/43/55. Generic branding does not authorize firmware. Unknown/unsupported devices retain read-only/unsupported behavior. No device table, EC address, WMI command, fan value, thermal floor or sensor map was changed.
- The existing capability gate serializes firmware operations and requires selected backend/service evidence. Synthetic tests cover unsupported states, AC restrictions, failed writes, missing sensors, fan Auto recovery, concurrent operations, startup preferences and Classic/Jelli projection. This does not prove physical behavior on any BIOS or OEM-service version.
- Updater downloads an executable, not an archive. No archive extraction path was found in that mechanism. Service installers use fixed tool/service operations and consent; tests never run them against this machine. Registry settings are still treated as untrusted preferences, not executable definitions or firmware protocol configuration.
- Native review covered bounded TCP-table parsing, reply framing, native allocations, Windows display/ETW layouts, NVML and WebView2 loading. Original native/Windows service implementations are retained. There is no replacement OEM driver, new telemetry endpoint or broad new JavaScript host object.
- Before this pass there was no tracked Actions workflow or security disclosure policy. The new Windows workflow has read-only contents permission, immutable action refs, credential-free checkout and no publishing step. Repository security settings and branch protections are owner actions, not silently changed from code.
- Repository/history scanning returned no secret findings, with two binary/large objects skipped by the scanner. This is a limited custom scanner result, not comprehensive entropy scanning or a proof about embedded binary content. No credential rotation was triggered by an actual discovered secret. Gitleaks, TruffleHog and CodeQL were not installed/run.

## Residual validation and owner actions

**CI publication status:** the completed workflow remains local at `.github/workflows/security-checks.yml`, as requested by the owner after GitHub rejected the initial push for missing OAuth `workflow` scope. Only source fixes, the test runner and these reports are being published to `revisions`; hosted Actions has not run. The full local review, including the workflow, is preserved on the local branch `audit/security-review-with-ci`.

1. **Before release:** validate signed update success/failure, publisher renewal/key change, revoked/tampered samples, interrupted replacement and rollback in a disposable elevated Windows VM. Protect signing keys outside the repo. Unsigned upgrades require manual installation.
2. Validate real WebView2 rendering, protected UDF sandbox access, external navigation/resource blocking, service-worker/cache poisoning and fallback; test ordinary and redirected/cloud folders. Source parser tests do not validate Chromium behavior.
3. Provision actual same-user mixed-integrity and different-user/session pipe clients; validate GUI/SYSTEM task overlap, task registration and service failure/repair without touching production devices. Named-object DoS remains a documented limit.
4. Physically validate supported Predator/Nitro configurations: fans/Auto recovery, power transitions, keyboard, MUX, sensors, battery reports/limits, hotkeys and startup/shutdown. No real hardware writes were automated.
5. Rebuild and sign new release artifacts, reconcile/remove stale distribution copies through a separate owner-reviewed publication change, designate supported releases, enable private reporting and require CI/branch protections. Existing artifacts and `master` are not changed by this audit.
6. Triage the remaining broad analyzer warnings separately. Many concern WinForms ownership, exception policy, naming and context use; none were blanket-suppressed to obtain green builds.

## Outcome and confidence limits

One controlled, reproduced filesystem vulnerability was found and fixed. Three additional confirmed unsafe trust/authorization/concurrency behaviors (A02/A03/A08) were hardened, alongside the potential WebView profile boundary and reliability/defense improvements above. **Zero complete local-to-administrator or remote-code-execution exploit chains were executed or claimed.** The highest remaining assessed risk is **High conditional distribution risk** while users run old artifacts; INF membership and real Windows/browser/hardware integration remain unvalidated. No dead-code/component/dependency removal was justified beyond replacing unsafe implementations. Final command results, including expected negative-regression failures and analyzer warnings, are in `VERIFICATION_RESULTS.md`.

## Primary references used for implementation review

The bridge design follows Microsoft's advice to validate document sources and message parameters and restrict host capabilities. See [WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security). Identification and failure-closed impersonation checks follow [ImpersonateNamedPipeClient](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient); [PipeOptions](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions) also documents elevation-sensitive same-user semantics.

Filesystem implementation was checked against [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes), [NtCreateFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile) and [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information). Controlled Windows tests, rather than documentation alone, verify the substitution behavior described in A01.
